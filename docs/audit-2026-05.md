# statico — Comprehensive Audit (May 2026)

**Branch:** `audit/2026-05-comprehensive-review`
**Scope:** Functionality, ease-of-use, competitive positioning, security
**Methodology:** source review across 30+ files, dogfooding `statico analyze .` on this repo,
`cargo test` / `cargo clippy`, web research on competitors (knip, biome, oxlint, cargo-shear,
cargo-machete, cargo-udeps, semgrep, CodeQL, SonarQube, etc.).

This audit complements (does not replace) the prior internal red-team passes — seven of them
resolved most known security issues before this branch was cut. New findings below focus on
what those passes did **not** cover: DX defaults, functional parity with peer tools,
doc/code drift, and remaining hardening opportunities.

---

## Severity Legend

- **P0** — blocks first-run UX or contradicts documentation
- **P1** — competitive parity gap or material correctness/security risk
- **P2** — quality polish; strong-want for adoption
- **P3** — nits

## Section 1 — Functionality

### F1.1 [P0] Doc / code drift: Cargo.toml description is stale
- `Cargo.toml:5` description: *"Static code analyzer for TypeScript projects"*
- README, CLI `--about`, `lib.rs` all advertise **TypeScript and Rust**.
- `crates.io` would publish the wrong description today.
- **Fix:** update `Cargo.toml` description to match.

### F1.2 [P1] Doc / code drift: `CLAUDE.md` says oxc is the TS parser; codebase uses tree-sitter
- `CLAUDE.md:25` lists `oxc` as a key dependency for TypeScript/JSX.
- Actual `Cargo.toml` uses `tree-sitter` + `tree-sitter-typescript`. `oxc_resolver` exists but
  is gated behind the optional `deep-resolution` feature.
- Misleads contributors and AI assistants reading the project context.
- **Fix:** rewrite `CLAUDE.md` parser section, document the optional `oxc_resolver` feature.

### F1.3 [P2] Unused field warning fails strict-warning builds
- `cargo build --release` reports: `field 'root' is never read` at `src/plugin/pipeline.rs:20`.
- Anyone building with `RUSTFLAGS="-D warnings"` (common in CI) hits a hard failure.
- **Fix:** remove the field or annotate `#[allow(dead_code)]` with a reason.

### F1.4 [P1] `--no-cache` flag is undocumented in README
- `analyze` exposes `--no-cache` (the change in commit `8b0c9b9`) but the CLI flag table in
  `README.md` only lists `--format`, `--min-confidence`, `--exit-code`.
- **Fix:** add the row to README.

### F1.5 [P2] `analyze` and `tui` defaults disagree on `--min-confidence`
- `analyze` defaults to `0.0` (show everything).
- `tui` defaults to `0.5`.
- Two views of the same project show different counts. Document or align.

### F1.6 [P2] No `--fix` apply mode (parity with knip / biome / cargo-shear)
- Statico's `fix` *output format* is hint-only — it prints `git show` commands.
- Knip, biome, oxlint, cargo-shear all auto-apply unused-import / unused-export removal.
- High signal feature for adoption; safe-by-default-with-dry-run is achievable.

### F1.7 [P2] No baseline / suppression file
- Tools like SonarQube and biome have project baselines so teams can ratchet down issues
  from a fixed starting count without each PR drowning in noise.
- Statico has `--exit-code` + `--min-confidence` only. There is no per-issue suppression and
  no JSON file consumed as a "known issues" baseline.

### F1.8 [P3] Plugin `discover_entries` listed as `[override only]` in the help text
- `src/commands/plugin.rs:97-98`. The README plugin docs imply pluggable discovery, but
  `override only` means a plugin replaces (not augments) entry detection. Document the
  consequence — turning on an entries plugin disables built-in framework detection.

## Section 2 — Ease of use / DX

### D2.1 [P0] Default exclusion list is missing common cache/build directories
- `src/discovery/mod.rs:186-202` `is_skipped_dir` skips: `node_modules .git dist build out
  .next .nuxt coverage .cache target .turbo`.
- **Missing:** `.angular`, `.svelte-kit`, `.vite`, `.parcel-cache`, `__pycache__`, `vendor`,
  `bower_components`, `.yarn`, `.pnp.*`, `.serverless`, `.vercel`, `.output`, `.astro`,
  `.docusaurus`, `.expo`, `.terraform`, `target/debug` already covered by `target`.
- **Live evidence:** running `statico analyze .` on this repo today flags 23k-line
  `website/.angular/cache/.../express.js` files as P0 dead code. Health score: 0/100.
  First-run UX for any Angular/Vite/Astro user is destroyed.
- **Fix:** extend `is_skipped_dir`. Optionally: in addition, walk `.gitignore` and
  auto-skip its directory entries (knip does this).

### D2.2 [P1] No default `exclude` list inside config defaults
- The README config example shows `exclude = ["node_modules", "dist", ...]` but the *default*
  `StaticoConfig::default()` has empty `exclude`. Users must opt-in to sensible behavior.
- Combined with D2.1, the noise for first-time users is severe.

### D2.3 [P1] Default output format `json` is hostile to first-run terminals
- `statico analyze .` with no flags dumps raw JSON to a tty. Knip/biome/oxlint default to
  human-readable. Detect tty and default to `markdown`/`pr-comment`-like, fall back to JSON
  when piped.

### D2.4 [P1] No `npx statico` / npm distribution
- Knip, biome, oxlint all install via npm. JS-first teams will not `cargo install` to try a
  TS analyzer. Provide a thin npm wrapper that downloads the right release binary
  (precedent: `@biomejs/biome`, `swc-cli`, `esbuild`).

### D2.5 [P2] No watch mode
- The incremental cache already exists (commit `8b0c9b9`). `--watch` is then mostly an
  fs-events loop — high value, low cost.

### D2.6 [P2] No official GitHub Action
- Lower the bar for CI adoption. SARIF output already exists; an Action that runs `analyze`
  and uploads SARIF is ~30 lines.

### D2.7 [P3] Init wizard
- `statico init` configures the shell, but there is no `statico init-config` to write a
  starter `.statico.toml` with sensible excludes for the detected framework.

## Section 3 — Competitive positioning

(Full landscape gathered from `knip`, `biome`, `oxlint`, `ts-prune`, `cargo-machete`,
`cargo-shear`, `cargo-udeps`, semgrep, CodeQL, SonarQube, Code Climate.)

### Real moats (lean into these)

1. **Polyglot — TS + Rust in one binary.** Nothing else in the audit covers both with the
   same depth. knip is TS-only; cargo-shear is Rust-only.
2. **AI-token-optimized outputs (`ai`, `context`).** Genuinely rare; competitors emit
   markdown/SARIF/CodeClimate but no compact LLM payload.
3. **Polyglot stdio plugin host.** LSP-style JSON-RPC over stdin/stdout with auto-runtime
   for Bun/Cargo/Python. knip's plugin model is in-process JS only; semgrep's is YAML rules.

### Parity gaps (must close)

| Feature | Statico | knip | biome | oxlint | cargo-shear |
|---|---|---|---|---|---|
| `--fix` apply mode | ❌ | ✅ | ✅ | partial | ✅ |
| Watch mode | ❌ | ✅ | ✅ | partial | ❌ |
| LSP / IDE integration | ❌ | partial | ✅ | ✅ | ❌ |
| GitHub Action | ❌ | ✅ | ✅ | ✅ | ❌ |
| npm distribution | ❌ | ✅ | ✅ | ✅ | n/a |
| Baseline file | ❌ | ✅ | ✅ | ❌ | ❌ |

### Reductive but useful: 0-100 health score
- Of the tools surveyed, only Code Climate emits a single project grade (A-F). Sonar and
  CodeQL avoid it. Statico's 0-100 score is a positioning win **if** the formula is
  defensible and stable — today, the cache-file inflation in D2.1 makes it actively
  misleading on real projects.

## Section 4 — Security (delta from prior red-team passes)

The seven prior red-team passes are thorough. New observations:

### S4.1 [P1] Bun runtime download is not integrity-verified
- `src/plugin/runtime.rs:87-171` `download_bun()` fetches Bun from
  `github.com/oven-sh/bun/releases/latest/download/...`, size-caps at 200 MB, then unzips
  and runs `--version`.
- This mirrors **F-12** (self-update binary not integrity-verified) for a *second* binary
  the user ends up executing. A compromised oven-sh release or MITM gives arbitrary code
  execution under the user's account, scoped to anyone running TS plugins.
- **Fix:** publish a known-good Bun SHA-256 list keyed by version+arch (or pin to a
  specific Bun version statico has tested), verify after download.

### S4.2 [P2] `download_bun` shells out to `unzip`
- Same file, line 124. The args are passed via `Command::new`/`args(...)` (no shell), so
  there's no injection — but **alpine/musl/minimal containers don't ship `unzip`**. The
  failure mode is just `Failed to run unzip: ...` which doesn't tell users to install it.
- **Fix:** use the `zip` crate for pure-Rust extraction (no new build prerequisite at
  runtime) or, at minimum, surface a clear "install unzip" error.

### S4.3 [P3] `which` subprocess is non-portable
- `runtime.rs:206` and `commands/doctor.rs` use `Command::new("which") ...`. Windows ships
  `where`, not `which`. The codebase already targets non-Windows for builds (only macOS &
  Linux are supported per `update.rs::platform_triple`), so this is not exploitable, but
  `commands/init.rs` currently allows `bash`/`zsh`/`fish` only — clarify Windows-not-
  supported in the README.

### S4.4 [P3] `init` shell snippet for fish does not quote the path
- `commands/init.rs:65`: `set -gx PATH {bin_dir_escaped} $PATH` — the path is escaped for
  bash double-quote semantics but used unquoted in fish. Spaces in the install path would
  break the snippet. Quote with single quotes for fish or use `set -gx PATH "$(printf '%s'
  ...)" $PATH`.

### S4.5 [Info] `download_bun` followed by `--version` exec
- The verification `target.exec("--version")` runs the just-downloaded binary before
  checksum verification. Order should be: download → SHA-256 verify → exec. Pair with
  S4.1.

### S4.6 [Info] CI strict mode broken by 70 clippy errors
- `cargo clippy --all-targets -- -D warnings` fails with 70 errors (mostly in test code:
  `manual_range_contains`, `useless_vec`, `assertions_on_constants`).
- Not a security finding by itself, but blocks adopting `-D warnings` as a CI gate, which
  is the standard Rust hardening practice.
